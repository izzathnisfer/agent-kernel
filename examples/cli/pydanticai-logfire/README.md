# Agent Kernel + Pydantic AI + Pydantic Logfire

This demo is the plain [`examples/cli/pydanticai`](../pydanticai) agents (a `triage` agent that
delegates to `math` / `weather` / `general` specialists) with **one change**: a `config.yaml` that
turns on Agent Kernel tracing and routes it to **Pydantic Logfire**. The agent code in `demo.py` is
byte-for-byte the same — tracing in Agent Kernel is transparent, so you observe the agents without
touching them.

```yaml
# config.yaml
trace:
  enabled: true
  type: logfire
```

## What is Logfire, and how does it differ from Langfuse / OpenLLMetry?

Logfire is Pydantic's observability platform, built directly on **OpenTelemetry**. Two things make
it distinct for this evaluation:

- **First-class Pydantic AI support.** The provider calls `logfire.instrument_pydantic_ai()`, so
  every model request, tool call, and structured-output validation shows up as a properly nested
  span with Pydantic AI's own semantics — no third-party instrumentor in between. (The OpenAI
  Agents SDK path gets the same first-class treatment via `logfire.instrument_openai_agents()`.)
- **Auto-detected destination.** Configured with `send_to_logfire="if-token-present"`:
  - **With a token** → spans stream to the hosted **Logfire dashboard**.
  - **Without a token** → spans print to the **console**, so the example runs with zero signup.

Because Logfire *is* an OpenTelemetry tracer provider, the other frameworks reuse the OpenInference
instrumentors already shipped with their extras (CrewAI, Google ADK) or their native OTel output
(Smolagents), and LangGraph's LiteLLM calls are captured via `logfire.instrument_litellm()`.

| | Langfuse | OpenLLMetry (Traceloop) | **Logfire** |
| --- | --- | --- | --- |
| Backend | Langfuse cloud/self-host | OTel → any collector | Logfire cloud **or console** |
| Pydantic AI | via OpenInference span processor | `Agent.instrument_all()` | **native `instrument_pydantic_ai`** |
| Runs with no account | no (needs keys) | needs a collector | **yes (console fallback)** |

## Model provider

`agentkernel[pydanticai]` installs the provider-agnostic `pydantic-ai-slim` core only. This demo
declares `pydantic-ai-slim[openai]` and uses `openai:gpt-4o-mini`, so it needs an `OPENAI_API_KEY`.
Switch providers with a one-line change to the model string in `demo.py`.

## Viewing traces

**Option A — Logfire cloud (hosted UI, recommended for the evaluation).** Authenticate once, which
writes a local credential the SDK auto-detects:

    uv run logfire auth

…or export a write token from your Logfire project:

    export LOGFIRE_TOKEN="your-write-token"

Then run the demo (below) and open the project dashboard — you'll see one trace per turn, with the
`Agent Kernel Pydantic AI` span at the root and the model/tool spans nested under it.

**Option B — console only (no signup).** Do nothing. With no token present, Logfire prints each span
to the console as the agent runs, so you can inspect the trace tree inline.

Optional environment variables: `LOGFIRE_SERVICE_NAME` overrides the service name (default
`AgentKernel`); Logfire's own variables (e.g. `LOGFIRE_CONSOLE=false`) tune console output.

## Running

The `pydanticai` and `logfire` extras are not on PyPI yet, so **build against the locally built
wheel** — first build it once from the repo root, then build this example:

    (cd ../../../ak-py && uv build --wheel)   # refresh ak-py/dist after any ak-py source change
    ./build.sh local                          # installs agentkernel from ak-py/dist + the logfire extra

Plain `./build.sh` (PyPI mode) will **not** work until the extras ship — it silently omits the
`logfire` package and the demo fails with `requires the 'logfire' extra`.

Run the demo with the example's own interpreter (avoid `uv run …` here — it re-syncs from PyPI and
can undo the local install):

    export OPENAI_API_KEY=sk-...     # the agents use openai:gpt-4o-mini
    .venv/bin/python demo.py

To run tests:

    .venv/bin/python -m pytest -s

> Note: until a release of `agentkernel` that includes the `pydanticai` and `logfire` extras is
> published to PyPI, build with `./build.sh local` against a locally built `ak-py/dist`. The
> committed `uv.lock` is generated by the release tooling once the extras ship.
